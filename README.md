# 分拣过机台（Sortbay）

骨架：过机扫描装载 → 口门路由裁决 → 错分回流批次 → 封袋班次对账

- 前端 http://127.0.0.1:6600
- API http://127.0.0.1:11600

## 软容量闸（全局唯一口径：超软容量硬拒）

本系统在题目给出的两种可行架构中，全局只贯彻一种：**以超软容量硬拒为准**。

- 在口件数是**派生口径**：`scans.status IN ('已路由','已入袋')` 且挂在该口门。
  含已入袋（袋未封口仍在格口），不含已封袋 / 错分回流 / 待路由。不存在可旁路直接改写在口数的接口。
- 当 `在口件数 >= chutes.soft_cap`（贴线）时，下一笔 `POST /api/扫描/{id}/路由`
  **整笔失败（HTTP 400，`原因码=SOFT_CAP_REJECT`）并回滚落入**：
  不写 scans 状态/chute_id、不写 route_events；扫描保持 `待路由/错分回流` 可再裁决前态；在口数不变。
- 拒绝事实仍独立提交：审计动作 `软容量硬拒` + 容量账本 `kind=裁决硬拒, delta=0`，可重放。
- 并发双落入 / 双击 / 多人抢最后一个位置：裁决事务用 `BEGIN IMMEDIATE`
  （`app/db.py::write_immediate`）把“核对容量 + 写入落入”串行化，容量为 C 时恰好 C 笔成功，绝不双破。
- 下调软容量会产生“当前已超容”的口门；超容事实在**裁决回执、口门页/`GET /口门`、
  `GET /软容量`、总览 `超容口门`、审计**同口径暴露。超容口门**仍可开袋/入袋/回流/封口**
  （集包泄压，不是“落入”），容量闸只拦裁决落入。
- 容量账本 `chute_capacity_ledger` 追加每次 +1（路由落入）、-1（错分回流）、
  封口负差（封袋移出）、0（硬拒/软容量调整，带容量快照）。
  `SUM(delta)` 恒等于派生在口数，半截回滚后也一致，可经下列端点重放。

### 相关接口

| 面 | 接口 |
| --- | --- |
| 裁决入口（回执） | `POST /api/扫描/{id}/路由` |
| 扫描册 | `GET /api/扫描[?状态=]`（含 `口门码/可再裁决`） |
| 口门在口数/告警 | `GET /api/口门`、`GET /api/口门/{id}` |
| 软容量设置 | `POST /api/口门/{id}/软容量?软容量=N`（也支持 PATCH/PUT、JSON `{软容量|soft_cap}`、`POST /api/口门/软容量`） |
| 全局软容量 | `POST /api/设置` `{"键":"口门软容量提示","值":N}`（批量同步所有口门） |
| 容量中心 | `GET /api/软容量`（策略 + 口门容量 + 超容/贴线名单） |
| 封袋集包 | `GET /api/封袋`、`POST /api/封袋/开袋`（超容不拦，回执带 `超容`） |
| 回流入口 | `POST /api/回流批次`（在口 -1，回执带新在口数） |
| 总览对账 | `GET /api/总览`、`GET /api/总览/对账` |
| 班次对账 | `GET /api/班次/对账`（含 `超容口门/容量对账一致`） |
| 审计 | `GET /api/审计` |
| 容量重放 | `GET /api/审计/重放?口门编号=`（别名 `/api/审计/replay`、`/api/口门/{id}/重放`、`/api/口门/{id}/对账`） |

策略标识在 `GET /api/健康`、`GET /api/总览`、`GET /api/软容量` 中以
`软容量策略="硬拒"` / `容量口径` 机器可核。
